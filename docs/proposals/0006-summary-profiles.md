# Настраиваемые профили саммари

## Пользовательский сценарий

Пользователь один раз создаёт профиль «Еженедельный статус»: русский язык, короткий контекст,
отдельные блоки рисков, решений и задач. При следующих запусках он выбирает профиль вместо ручной
настройки mode/provider. Другой профиль оформляет лекцию как конспект, третий — интервью как
вопросы, ответы и цитаты.

Профиль описывает желаемый результат, а не конкретный LLM. Его можно применить к существующему
transcript, сравнить с другим профилем и экспортировать вместе с результатом для воспроизводимости.

## Первичная оценка

| Аспект | Оценка | Обоснование |
|---|---|---|
| Пользовательская ценность | высокая для повторяемых процессов | Один и тот же тип встречи получает предсказуемую структуру |
| Сложность MVP | средняя | Текущие modes и свободные блоки MeetingSummary дают основу без смены pipeline |
| Риск качества | средний | Произвольные инструкции могут конфликтовать, раздувать prompt или ломать round-trip |
| Риск совместимости | средний | Профиль должен переживать смену provider и развитие schema |
| Рекомендация | начать с ограниченного конструктора | Сохранённые блоки и инструкции безопаснее произвольной JSON schema |

## Границы MVP

- встроенные неизменяемые профили для существующих `brief`, `medium`, `detailed`, `lecture`;
- создание пользовательского профиля из встроенного;
- имя, описание, язык результата, базовый mode и упорядоченный набор ожидаемых блоков;
- короткие дополнительные инструкции с лимитом длины и preview итоговой структуры;
- выбор default profile и per-run override;
- экспорт/импорт одного versioned profile-файла без API-ключей и локальных путей;
- повторная суммаризация существующего transcript другим профилем.

В MVP не входят произвольный executable/plugin, Jinja/Python templates, динамическая JSON Schema,
организационный marketplace, совместное редактирование и автоматический выбор профиля LLM-моделью.

## Модель данных и pipeline

`SummaryProfile` имеет стабильный ID, schema version, display metadata, language, base mode,
ограниченный список `BlockSpec` и additional instructions. Provider/model остаются настройкой run:
профиль не должен тайно привязывать результат к платному сервису или переносить credentials.

Factory продолжает быть единственной точкой создания summarizer. Новый profile compiler превращает
валидный профиль в system/user prompt и ожидаемую структурированную форму. Результатом остаётся
`MeetingSummary` с blocks, поэтому существующие plain/Markdown/HTML/JSON formatters и редактор не
получают отдельную ветку на каждый профиль.

Сохранённый результат фиксирует `profile_id`, версию и snapshot значимых полей. Если профиль позже
изменён, старое саммари остаётся воспроизводимым и не меняет смысл задним числом. Импорт нового
профиля проверяет версию, размеры, допустимые поля и конфликт ID до записи.

Transcript всегда помещается в отдельный data-container и не интерпретируется как часть template.
Дополнительные инструкции пользователя тоже проходят лимиты и не могут переопределить privacy,
tool access или формат transport-запроса. Это не делает LLM абсолютно устойчивой к prompt injection,
но сохраняет системную границу приложения.

## UX

- Конструктор использует формы «Добавить блок / описание блока», а не пустое поле системного prompt.
- Preview показывает структуру, пример и приблизительную стоимость контекста до сохранения.
- Built-in profile можно клонировать, но нельзя незаметно изменить обновлением приложения.
- Несовместимый provider объясняет ограничение structured output и предлагает fallback, не теряя
  профиль.
- Выбор профиля виден в истории и на экране результата.
- Результаты двух профилей можно создавать из одного transcript без повторного Whisper run.

## Этапы реализации

1. Определить versioned `SummaryProfile`/`BlockSpec` и правила compilation.
2. Представить текущие четыре modes как built-in profiles без изменения их поведения.
3. Добавить profile store, import/export и validation tests.
4. Передать compiled profile через factory/workflow с сохранением MeetingSummary boundary.
5. Реализовать selector, ограниченный конструктор и preview.
6. Добавить snapshot профиля в structured result/library и сценарий повторной суммаризации.

## Открытые решения

- Какие свойства блока нужны кроме заголовка, описания и максимального числа пунктов?
- Разрешать ли профилю выбирать chunk merge strategy для длинных transcript?
- Нужно ли разделять язык интерфейса профиля и язык итогового саммари?
- Где хранить profile snapshots: рядом с summary JSON или в локальной библиотеке?
- Как отображать результат, если модель не заполнила обязательный блок?

## Критерии готовности

- Built-in profiles воспроизводят поведение существующих modes на regression fixtures.
- Пользователь создаёт, выбирает, экспортирует и повторно импортирует профиль без секретов.
- Один transcript суммаризируется разными профилями без повторной транскрибации.
- Старый результат сохраняет snapshot после изменения или удаления исходного профиля.
- Невалидный, чрезмерный или несовместимый profile отклоняется до LLM-вызова.
- Результаты проходят существующий MeetingSummary render/parse round-trip.
- Profile не может изменить provider credentials, output path или privacy consent.
