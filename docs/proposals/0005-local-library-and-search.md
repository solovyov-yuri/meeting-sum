# Локальная библиотека и полнотекстовый поиск

## Пользовательский сценарий

Пользователь открывает Recap и находит прошлую встречу по словам из transcript или саммари,
участнику, дате, источнику, тегу или статусу. Из результата он открывает артефакты, повторяет
саммаризацию, экспортирует материалы или замечает, что исходный файл был перемещён.

Сейчас история является коротким JSON-списком ссылок на файлы. Она подходит для повторного открытия
последних запусков, но не является масштабируемым каталогом и не индексирует содержимое. Это
предложение превращает desktop-приложение в локальную библиотеку, не делая облачное хранилище
обязательным.

## Первичная оценка

| Аспект | Оценка | Обоснование |
|---|---|---|
| Пользовательская ценность | высокая и накопительная | Чем больше результатов, тем важнее повторный поиск и организация |
| Сложность MVP | средняя | SQLite и локальный FTS хорошо изолируются от media/LLM pipeline |
| Риск миграции | средний | Нужно импортировать history без потери ссылок и уметь восстановить индекс |
| Privacy-риск | средний | Полнотекстовый индекс содержит чувствительный текст, хотя остаётся локальным |
| Рекомендация | ранний кандидат | Даёт основу для source metadata, tags, actions и будущих интеграций |

## Границы MVP

- единая библиотека запусков с поиском по transcript, summary и названию;
- фильтры по дате, run mode, provider, status и типу источника;
- пользовательские теги и необязательное отображаемое название;
- сортировка, пагинация и состояния отсутствующих/перемещённых файлов;
- переиндексация одного результата и полная безопасная перестройка индекса;
- одноразовый импорт существующего `history.json` с резервной копией;
- локальная работа без аккаунта, сервера и сетевого поиска.

В MVP не входят облачная синхронизация, совместная библиотека, semantic/vector search, автоматические
темы, OCR вложений и управление исходными аудиофайлами как медиатекой.

## Предлагаемая архитектура

SQLite-каталог заменяет `history.json` как metadata store и использует встроенный полнотекстовый
индекс для нормализованного transcript/summary. Файлы результатов остаются переносимыми
артефактами и источником для экспорта; индекс — производное представление, которое можно
перестроить. Схема имеет явную версию и последовательные migrations.

Application repository предоставляет операции `record_run`, `search`, `get_item`, `update_tags`,
`delete_from_library` и `reindex`. CLI, desktop bridge и будущий agent gateway не выполняют SQL
напрямую. Запись terminal result и путей происходит в одной транзакции, а индексирование текста
может безопасно повторяться после сбоя.

Файлы за пределами app-data читаются только если они уже зарегистрированы результатом run или
явно импортированы пользователем. Это сохраняет действующую защиту bridge от произвольного чтения.
Удаление записи из библиотеки и удаление файлов — разные действия с отдельным подтверждением.

Для переносимости библиотека хранит нормализованные абсолютные пути и устойчивые идентификаторы,
но умеет повторно привязать перемещённую папку результатов. Source metadata из URL-import и
будущей записи добавляются типизированными полями, а не произвольным JSON без версии.

## Поиск и UX

- Поиск по умолчанию локальный и объяснимый: совпавший фрагмент подсвечивается.
- Пустой запрос показывает недавние результаты; фильтры отражены в URL/state интерфейса.
- Отсутствующий файл не удаляет карточку молча: предлагаются locate, убрать из библиотеки или
  оставить запись.
- Теги принадлежат библиотеке и не модифицируют пользовательский transcript/summary.
- Пользователь может исключить отдельный результат из полнотекстового индекса, сохранив metadata.
- Экспорт/backup базы не должен незаметно включать исходное аудио.

## Приватность и надёжность

Индекс содержит копии текста для поиска и поэтому защищается теми же правами профиля пользователя,
что app-data. Текст не пишется в диагностические логи и не отправляется в telemetry. Шифрование
базы не входит в MVP: без безопасного управления ключом оно создаст видимость защиты, пока сами
экспортированные `.txt` остаются открытыми. Возможность шифрованного workspace требует отдельного
решения для всех артефактов, а не только индекса.

Повреждённая база не должна лишать пользователя файлов. Recap создаёт новую базу, предлагает
rebuild и сохраняет повреждённую копию для ручного восстановления. Migration сначала создаёт backup
и не удаляет `history.json`, пока новый каталог не прошёл проверку.

## Этапы реализации

1. Зафиксировать catalog schema, migration policy и repository interface.
2. Реализовать SQLite repository, FTS и тесты транзакций/миграций/повреждения.
3. Импортировать history и индексировать существующие зарегистрированные результаты.
4. Перевести bridge history commands на repository с сохранением UI-контракта.
5. Добавить search/filter/tag UI и обработку missing paths.
6. Добавить backup/rebuild и soak test на десятках тысяч записей.

## Открытые решения

- Следует ли индексировать transcript автоматически или запрашивать opt-in при первом запуске?
- Какие языковые tokenizer/stemming нужны для русского и английского поиска?
- Нужна ли библиотеке концепция project/folder поверх тегов уже в первом релизе?
- Как долго хранить карточку failed/cancelled run без полезных артефактов?
- Должна ли повторная суммаризация создавать новую карточку или версию существующего результата?

## Критерии готовности

- Миграция существующей истории идемпотентна и не теряет ни одной валидной ссылки.
- Поиск находит слова из transcript и summary с фильтрами и контекстным фрагментом.
- Десятки тысяч карточек не требуют чтения всех файлов при каждом открытии экрана.
- Повреждение или удаление базы не уничтожает пользовательские артефакты; rebuild возвращает
  доступные результаты.
- Перемещённые и отсутствующие файлы диагностируются без зависания и тихого удаления.
- Bridge по-прежнему не читает произвольный путь, переданный webview.
- Delete from library и delete files невозможно перепутать одним неявным действием.
