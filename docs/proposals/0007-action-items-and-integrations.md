# Задачи и интеграции с рабочими системами

## Пользовательский сценарий

После встречи Recap показывает отдельный список найденных задач: текст, ответственный, срок и
ссылка на фрагмент transcript. Пользователь исправляет поля, отклоняет ложные задачи и только затем
экспортирует подтверждённые элементы в файл, календарь или подключённый task tracker. Повторный
экспорт не создаёт дубликаты.

Сегодня задачи существуют как строки внутри блоков `MeetingSummary`. Этого достаточно для чтения,
но недостаточно для надёжной интеграции: приложение не может отличить владельца от текста,
проверить дату или сохранить ID созданного внешнего объекта.

## Первичная оценка

| Аспект | Оценка | Обоснование |
|---|---|---|
| Пользовательская ценность | высокая для рабочих встреч | Сокращает разрыв между протоколом и исполнением решений |
| Сложность локального MVP | средняя | Typed actions, review UI и CSV/ICS не требуют OAuth |
| Сложность внешних adapters | высокая | OAuth, scopes, API drift, rate limits и дедупликация различаются по системам |
| Риск ошибки | высокий без подтверждения | LLM может придумать владельца, срок или саму задачу |
| Рекомендация | local-first, human-in-the-loop | Сначала достоверная модель и review, затем одна внешняя интеграция |

## Границы MVP

- типизированный `ActionItem`: текст, owner, due date, status, confidence и ссылки на evidence;
- извлечение задач как часть structured summary с сохранением исходной формулировки;
- отдельный review screen: подтвердить, исправить, отклонить;
- локальные экспорты Markdown/CSV и календарный `.ics` только для элементов со сроком;
- copy-to-clipboard в предсказуемом формате;
- состояние экспорта и idempotency key для будущих adapters;
- отсутствие автоматической публикации при завершении саммаризации.

В MVP не входят автоматическая рассылка участникам, фоновая синхронизация, двустороннее обновление,
назначение пользователя по имени без подтверждения и одновременная поддержка множества внешних
систем.

## Модель данных

`MeetingSummary` необходимо расширять совместимо: человекочитаемые blocks остаются, а typed
`actions` становятся отдельным структурированным полем с устойчивыми IDs. Formatter строит раздел
«Решения и задачи» из этих объектов, чтобы JSON и текст не расходились. Парсинг вручную
отредактированного plain/Markdown не должен притворяться, что надёжно восстановил owner/due:
неоднозначные значения остаются текстом до review.

Evidence содержит ID/timestamp сегмента и короткую цитату, но не отдельную копию полного
transcript. Due date хранится в ISO-форме вместе с исходным текстом и timezone context. Если дата
не названа явно, LLM не подставляет удобное предположение; поле остаётся пустым.

Локальный action repository хранит review state и export receipts отдельно от текста саммари.
Это позволяет повторно сгенерировать summary, не потеряв уже подтверждённую задачу, и не создавать
дубликат после retry внешнего вызова.

## Adapter boundary

Внешняя система подключается узким adapter interface: `validate_connection`, `preview`, `create`
и при необходимости `get`. Adapter получает только подтверждённые поля и idempotency key, не весь
transcript. OAuth tokens живут в OS keychain; scopes минимальны и показываются до подключения.

Первый внешний adapter выбирается после проверки реального спроса. До этого CSV/ICS являются
полезным универсальным контрактом и позволяют проверить модель данных без преждевременной
зависимости от конкретного vendor API. Интеграция с пользовательскими агентами из proposal 0001
может читать подтверждённые actions через тот же application service, но не обходить review policy.

## UX и безопасность действий

- Любая внешняя запись показывает destination, проект/календарь и точный preview.
- По умолчанию выбраны только явно подтверждённые пользователем элементы.
- Имя из transcript не сопоставляется аккаунту внешней системы без явного выбора.
- Batch publish возвращает результат по каждому элементу; частичный сбой можно безопасно повторить.
- Удаление внешней задачи не выполняется автоматически при удалении истории Recap.
- Логи не содержат OAuth token, полный transcript или приватный ответ внешнего API.
- Prompt injection в transcript не может вызвать adapter: tools доступны только отдельному
  подтверждённому application flow после завершения LLM.

## Этапы реализации

1. Зафиксировать `ActionItem`, evidence и date/time semantics; обновить summary schema fixtures.
2. Сохранить обратную совместимость render/parse для старых summary и строковых actions.
3. Реализовать review state и UI редактирования/подтверждения.
4. Добавить Markdown/CSV/ICS export и idempotency tests.
5. Собрать метрики принятия/исправления задач и выбрать один внешний adapter.
6. Реализовать OAuth/keychain, preview/publish и contract tests для выбранной системы.

## Открытые решения

- Считать ли решения без действия отдельным типом или частью ActionItem?
- Как связывать owner с контактом, не создавая собственный справочник людей?
- Какая timezone используется для относительных сроков «завтра» и «к пятнице»?
- Должно ли редактирование саммари изменять typed actions или это два независимых представления?
- Какой task tracker или календарь имеет наибольшую ценность как первый внешний adapter?
- Нужна ли политика обязательного review для agent gateway, или агент может получить отдельное
  per-run разрешение на публикацию?

## Критерии готовности

- Каждая извлечённая задача имеет исходный текст и evidence либо явно помечена как неуверенная.
- Не названные owner и due date остаются пустыми, а не генерируются моделью.
- Пользователь видит и подтверждает точный набор до любого внешнего side effect.
- CSV/ICS проходят round-trip fixtures с Unicode, timezone и пустыми optional fields.
- Повтор publish после timeout не создаёт дубликат подтверждённой задачи.
- Partial failure показывает результат каждого элемента и допускает безопасный retry.
- Credentials остаются в keychain, а adapter не получает полный transcript без отдельной причины.
- Старые summary продолжают открываться и экспортироваться после расширения модели.
