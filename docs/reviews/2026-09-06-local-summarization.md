# Локальная суммаризация длинных транскриптов — 2026-09-06

## Что проверено

Windows, RTX 5070 12 ГБ, Ollama 0.32.5. Локальная `qwen3.5:latest` совпадает
с тегом `qwen3.5:9b` (метаданные: 9.7B, Q4_K_M). Дополнительно использована
уже установленная `qwen3:latest` (8.2B, Q4_K_M). Новые модели не скачивались.
Все реальные транскрипты отправлялись только на localhost.

В исходной реализации `options.num_ctx` через `/v1/chat/completions` игнорируется:
запрошенные 2048 дали фактические 4096; родной `/api/chat` применил 2048.
Это соответствует [документации Ollama](https://docs.ollama.com/api/openai-compatibility#setting-the-context-size).
Ограничение 42 000 символов транскрипта не учитывало окно, инструкции или ответ.

## Итоговая реализация

- Ollama использует родной API с явным контекстом, отключённым thinking, ограниченным
  ответом и `truncate: false`, `shift: false`. По умолчанию — 8192 токена.
- Вход оценивается как один токен на три байта UTF-8, с отдельным резервом под
  инструкции, схемы и ответ. Это эмпирическая оценка, а не точный токенизатор.
  На установленном сервере запрет обрезания проверен отдельно: искусственный
  запрос на 30 014 токенов при окне 4096 отклонён с HTTP 400.
- Модель выбирает индексы важных исходных отрывков. Код проверяет диапазон,
  количество и уникальность индексов, сохраняет исходный порядок и дословный текст.
  Отбор повторяется при необходимости; свободный пересказ происходит только в конце.
- Промежуточные результаты переиспользуются при повторе финального оформления.
  Пустой/оборванный ответ и несходящееся сокращение приводят к ошибке, а не к
  сохранению обрезанного результата. Явный режим `truncate` сохраняет прежний смысл.
- Есть прогресс по фрагментам и кооперативная отмена во время потокового ответа.
- Перед локальной Ollama в полном запуске выгружаются веса Whisper; при следующей
  транскрибации они автоматически загружаются обратно.

## Реальные прогоны

Режим `medium`, `qwen3.5:latest`, окно 8192. Один прогон на файл, без параллельных
LLM-запросов. Время включает вызовы модели, но не транскрибацию аудио.

| Транскрипт | Символов без таймкодов | Время | Результат |
|---|---:|---:|---|
| 2026-06-25 16-01-31 | 43 142 | 42,62 с | Успех |
| 2026-08-06 16-04-15 | 2 834 | 8,36 с | Успех |
| 2026-08-20 16-04-31 | 44 463 | 33,38 с | Успех |
| 2026-08-27 16-03-55 | 42 196 | 30,86 с | Успех |
| 2026-09-03 16-04-13 | 47 925 | 35,12 с | Успех |

На записи 3 сентября исходный алгоритм занял 96,92 с и выдал 2 общих пункта.
Итоговая реализация заняла 35,12 с и выдала 8 пунктов, охватив дополнительные темы:
распределение нагрузки, сокращение глубины хранения и сегментацию данных.
Это сравнение двух реализаций в целом, а не изолированный эффект одной настройки.

На той же записи с окном 4096: `qwen3.5:latest` — 92,33 с, `qwen3:latest` — 95,84 с,
оба прогона успешны. Полнота заметно ниже, чем при 8192. Более свободная оценка
токенов (байты / 4) экспериментально ускорила 4096, но не улучшила полноту;
в код она не включена. Повторные свободные пересказы промежуточных записей также
отклонены: они накапливали искажения условий и примеров.

Ollama сообщала около 5,48 GiB видеопамяти для qwen3.5 при 8192 и 5,25 GiB
при 4096; для qwen3 при 4096 — около 5,20 GiB. Это память модели по `/api/ps`,
а не требования ко всей машине. Первый замер 4096 захватил ранее загруженный
контекст 8192: его поле `peak_model_vram_bytes` непригодно для сравнения профилей;
значение 5,25 GiB подтверждено отдельным последующим замером уже при 4096.

Отдельно загружены кешированные веса Whisper large-v3 на CUDA:
общая занятая видеопамять была 5542 MiB до загрузки, 8677 после, 5701 после
выгрузки и снова 8677 после повторной загрузки. Выгрузка освободила 2976 MiB.

## Проверки и границы результата

- Полный Python-набор: 470 тестов. Ruff и mypy без ошибок.
- Реальный `recap-bridge resummarize` с отдельным каталогом настроек: успешное
  сохранение короткого саммари; отмена длинного на втором фрагменте вернула
  `cancelled`, транскрипт сохранён, файл саммари не создан.
- Прямой цикл загрузка → выгрузка → загрузка Whisper на CUDA проверен.
  Полный GUI-запуск, новая сборка приложения, CPU-only и машина с меньшей
  физической видеопамятью не проверялись.
- Успех генерации не означает полноты или фактической безошибочности. Просмотр
  результатов выявляет потери деталей при 4096 и отдельные неточности в условиях,
  числах и названиях при плохом ASR. Нет размеченного эталона и статистической оценки
  качества. Основной профиль — 8192; 4096 — компромисс с потерей подробностей.
- `resummarize` в отдельном процессе не может выгрузить Whisper, оставленный
  другим процессом после режима «только транскрибация».

Воспроизведение: `python scripts/benchmark_summaries.py --context 8192`.
Файлы, stdout/stderr экспериментов и результаты находятся в игнорируемом Git каталоге
`data/summary-benchmark/`; журналы `evidence-8192.log`, `evidence-4096.log`,
`evidence-qwen3.log` относятся к итоговому способу отбора. Сами транскрипты
и полные саммари не копировались в отслеживаемый отчёт.
