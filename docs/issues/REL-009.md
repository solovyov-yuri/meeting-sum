# REL-009: Вечное зависание pull модели при молчащем сокете

## Проблема

`pull_model` открывает стриминговый `/api/pull` с `timeout=None` и итерирует строки. Если Ollama
или сеть замирают между строками (полуоткрытый TCP, подвисший registry, сон машины), `for raw in
resp` блокируется навсегда. Проверка `cancel` стоит только **между** строками, поэтому «Отменить»
в `ModelDownloadDialog` не сработает: Rust-watcher запишет флаг-файл, но мост его никогда не
опросит. Для сравнения: соседний `cuda_support.download_cuda_libs` использует `timeout=60` и
опрашивает cancel в цикле чтения чанков.

## Доказательства

`src/ollama_support.py` прочитан целиком (2026-07-05): `_post(base_url, "/api/pull", …,
timeout=None)`; единственный опрос `cancel` — в начале итерации строки.

## Почему это важно

Это новый пользовательский флоу (коммит 8213732); pull многогигабайтной модели при нестабильной
сети — реалистичный сценарий. Единственный выход из зависания — убить приложение; UI навсегда
остаётся на «Загрузка модели…».

## Варианты решения

1. **(Рекомендуется)** `timeout=300` (idle-таймаут между чтениями; Ollama шлёт status-строки
   постоянно — 5 минут тишины = сбой). `socket.timeout`/`TimeoutError` всплывёт в существующую
   границу `desktop_bridge.pull_model` как `failed`.
2. Дополнительно: читать чанками с коротким таймаутом и опрашивать `cancel` по таймауту чтения —
   тогда отмена работает и при молчащем сервере.

## Как проверить исправление

Unit-тест с фейковым response, который блокируется/кидает `socket.timeout` → `pull_model`
завершается ошибкой, UI получает `failed`. Вручную — оборвать сеть во время pull.
