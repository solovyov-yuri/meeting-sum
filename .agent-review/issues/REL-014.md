# REL-014: Конкурентная ротация лога между worker- и one-shot-процессами

## Проблема

Каждый процесс моста — и долгоживущий worker (`recap-bridge serve`), и каждый one-shot вызов
(get_settings, export и т.п.) — открывает **один и тот же** `logs/recap-bridge.log` через
`RotatingFileHandler(maxBytes=1_000_000)`. На Windows `doRollover()` делает `os.rename` открытого
файла; пока worker держит лог открытым, rename из one-shot процесса упадёт с WinError 32
(sharing violation) — `logging` молча проглотит это в `handleError`, файл продолжит расти сверх
лимита. Практически ротация отключена всё время жизни worker-а, то есть почти всегда.

Механизм конкурентного открытия подтверждён кодом; точное поведение rename-под-открытым-хэндлом
на Windows отсюда не проверить — потому `evidence: hypothesis`. Подтвердит: нагнать лог >1 МБ
one-shot вызовами при работающем app и посмотреть, появился ли `recap-bridge.log.1`.

## Почему это важно

Лог моста — единственный технический след для разбора инцидентов (итог ARCH-004); молчаливо
сломанная ротация со временем даёт либо гигантский файл, либо потерю записей.

## Варианты решения

1. **(Рекомендуется)** Разделить файлы: worker пишет в `recap-bridge-serve.log`, one-shot — в
   общий `recap-bridge.log` (или `-{pid}` с чисткой старых при старте). Убирает конкуренцию
   принципиально.
2. Отключить ротацию по размеру и чистить по возрасту/размеру при старте процесса (когда файл
   гарантированно не занят другим ротатором).

## Как проверить исправление

На Windows: живой app (worker запущен), нагнать >1 МБ логов one-shot командами — ротация/чистка
работает, записи не теряются.
