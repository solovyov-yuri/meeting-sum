# SEC-006: Загрузка CUDA-wheels без верификации целостности

## Проблема

`_resolve_win_wheel()` берёт URL wheel-а из PyPI JSON API и игнорирует лежащее там же поле
`digests.sha256`. Скачанный файл сразу распаковывается — а это DLL-и, которые процесс затем
загружает и исполняет (`_set_cuda_paths` → ctranslate2). Версии пиннены, канал HTTPS — но это вся
защита: корпоративный TLS-прокси с подменным CA, компрометация CDN files.pythonhosted.org или
битая докачка дают неисполнимую диагностику в лучшем случае и исполнение чужого кода в худшем.

При этом точные sha256 нужных win_amd64-wheel-ов уже есть в репозитории — в `uv.lock`.

## Доказательства

`src/cuda_support.py`, `_resolve_win_wheel`: возвращает только `entry["url"]` и `size`; в цикле
загрузки `download_cuda_libs` нет ни `hashlib`, ни сверки с `digests`. Проверено чтением файла
целиком (2026-07-05).

## Почему это важно

Это единственное место проекта, где по сети скачивается исполняемый код на машину пользователя.
Отсутствие верификации превращает любую сетевую атаку или повреждение в исполнение кода либо в
загадочные падения GPU-режима без диагностики.

## Варианты решения

1. **(Рекомендуется)** Захардкодить sha256 для каждой пары (pkg, version) рядом с `CUDA_PACKAGES`
   (значения взять из `uv.lock`) и считать `hashlib.sha256` потоково при скачивании; несовпадение →
   `RuntimeError` (всплывёт как failed-шаг `download` в существующую границу). Синхронный бамп
   хэшей при бампе версий уже требуется докстрингом «must match pyproject.toml».
2. Минимум: сверять с `entry["digests"]["sha256"]` из того же PyPI JSON-ответа — защищает от
   битой докачки/CDN-повреждения, но не от MITM обоих запросов.

## Как проверить исправление

Unit-тест в `tests/test_cuda_support.py`: подменённое содержимое wheel-а → ошибка, сентинел
`.recap-cuda-complete` не записан, повторный запуск снова предлагает загрузку.
